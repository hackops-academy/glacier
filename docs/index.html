Why the proxy comes first

Every other tool in Glacier — spider, active scanner, repeater, fuzzer — either routes through the proxy or reuses the traffic it captured. The active scanner tests every query parameter on a URL against a battery of checks. Understanding what each check actually does — not just its name — is what lets you trust a result, explain it in a report, and eventually write your own checks.

Reflected XSS

Injects a marker string with HTML-breaking characters into a parameter, then checks whether it comes back in the response unescaped. Try it directly:

terminal
$ curl -s "http://127.0.0.1:5001/search?q=<script>test</script>" | grep -o "<script>test</script>"

If that comes back verbatim, the input reached the page without escaping — a real reflected XSS. Compare against /safe-search, which HTML-escapes the same input; the scanner correctly stays silent there.

SQL injection — three escalating techniques

CheckSignal it looks forTarget route
Error-basedA database error message (e.g. containing SQLSTATE) leaking into the response/product
Boolean-blindNo error shown, but the page's content differs between a true and a false condition ("in stock" vs "not found")/blind-product
Time-blindNeither an error nor a content difference — only a measurable response delay when a sleep condition is injected/slow-product

These run in escalating order precisely because each is progressively slower and noisier — the scanner only drops to boolean-blind if error-based finds nothing, and only to time-blind if boolean-blind finds nothing either.

Path traversal

Injects directory-traversal sequences at a few depths and encodings, then checks the response for content unique to /etc/passwd or windows/win.ini — files that are always present and harmless to read, but should never appear unless user input is reaching a file path unsanitized.

Command injection — why not just echo a marker

This is the check worth understanding in detail, because the obvious implementation has a real bug. A naive check injects ; echo MARKER and looks for MARKER in the response. The problem: if the app fails to run the command and just echoes the raw, unexecuted input back in an error message ("no such host: ; echo MARKER"), that string still shows up — a false positive with zero code execution involved.

Glacier's check instead injects an arithmetic expression — multiply two fixed numbers, e.g. ; expr 6247 \\* 8351 — and looks for the product in the response. The raw payload text never contains that product; it can only appear if a shell genuinely evaluated the expression. Same idea extends to the blind variant, which uses sleep and measures timing instead of output, for cases where nothing is ever reflected at all.

Open redirect

Injects absolute and bypass-style URLs (protocol-relative //host/, a backslash variant some parsers normalize into a slash) and inspects the Location header directly, without following the redirect — the vulnerable route copies the parameter straight into Location; the safe route validates it stays on-site first.

Run it for real

In the HUD's Active Scanner tab, target http://127.0.0.1:5001/product?id=1, check the authorization box, and start. Watch the progress messages — they'll name each check as it runs, in the same escalating order described above.

⚠️
The active scanner sends real, potentially destructive-looking test payloads. It requires the same explicit confirmation checkbox as Fuzzer, for the same reason.
✅
Checkpoint. Run a full active scan against every URL the spider discovered in Lesson 4. You should end up with findings across at least four different vulnerability classes. Keep this findings list — you'll turn it into a real report in Lesson 10.

Two ways to authenticate

Glacier's auth module supports both patterns you'll encounter in practice:

ModeHow it worksWhen to use it
cookiePaste an already-authenticated Cookie or Authorization header directly — grabbed from a logged-in browser tab or an API clientFastest option; works for any auth scheme since you're not modeling a login flow at all

Here's the part that matters on real engagements: a scan generates a lot of traffic in a row, which is exactly the kind of volume that can trip a session timeout on the target itself. Why phase 5 exists — and isn't optional

An automated scanner optimizes for not missing things, which means it will occasionally flag something that isn't actually exploitable in context. Shipping an unverified finding to a client is how you lose credibility fast. Before anything goes in a report, reproduce it manually in Repeater and capture the exact request and response as evidence.

Anatomy of a good finding

Every finding Glacier's active scanner produces already has this shape — it's not an accident, it's the template a real report entry needs:

FieldWhat goes here
NamePrecise, not vague — "Reflected XSS in q parameter of /search," not "XSS issue"
RiskImpact if exploited, not just "how it was found" — consider auth requirements, data exposed, blast radius
EvidenceThe literal payload and the literal response snippet that proves it — not a description of what you saw, the actual text
Steps to reproduceExact request, in enough detail that someone with zero context can confirm it themselves
RemediationSpecific and actionable — "parameterize the query" beats "improve input validation"

**Evidence:**
Request:  GET /product?id=1'
Response: HTTP 500
          "SQL error: SQLSTATE - unrecognized token: \\"'\\""

**Impact:**
The `id` parameter is concatenated directly into a SQL query with no
